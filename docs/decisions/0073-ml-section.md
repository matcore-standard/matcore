# 0073 — The ML section: the model, how it was built, and how the data came from it

Date: 2026-11-19. Status: accepted. Decided by: Ellad Tadmor.

## Context
MatCore documents the methods that generate a computational materials science dataset. The baseline ML section is a model card: it says what a model is and how it was trained. It says nothing about how the dataset was produced from the model. Take the section's own example, a set of crystal structures generated by WyFormer. The record names the architecture and the training set (MP-20), but not how many structures were sampled, under what conditioning, with what sampling settings, or what was discarded (invalid structures, duplicates, structures already in the training set).

Review on 2026-11-18 raised five points:
1. Is a machine-learned interatomic potential (MLIP) "Property prediction"?
2. Can the training, validation and test subsets be given explicitly?
3. Does `training-procedure` mean the loss, or should the loss be a property of its own?
4. Should `training-hyperparameters` have subproperties, and does it overlap `model-architecture` (layers, nodes)?
5. "Validation" strictly means the data used to tune hyperparameters; "testing" assesses the model.

On point 1: an MLIP is a particle interaction model (pim, theory-level Machine-learned; 0046). It is an ingredient used to generate data, not the data. The ML section does not describe it.

On point 2: a split is usually made at training time from percentages, and a sentence describes it fully. Structured subsets would be too specific.

Under 0046, ML work forms two computations, both of method ML:
- the training (task Training);
- the inference (task Structure generation, Property calculation, ...), which produces the dataset's content.

The inference names the training computation as input role Parameters. A model trained outside the record is named as the computation's software.

## Decision
1. **Settings.** ml's properties sit in a required, repeatable `settings` whose first member is `computation-label` (0046 item 7, 0062). The introduction gains 0054's sentence on settings blocks.

2. **`ml-task`** stays required but is no longer repeatable, since `type` already repeats. Its members:
   - `type*` names the kind of result the model produces. Open terms: Property prediction, Structure generation, Synthesis prediction, Ranking, Clustering, Embedding.
   - "Structure prediction" (a structure for a given composition) is merged into Structure generation as generation with a fixed composition.
   - "Material ranking" becomes Ranking.
   - Each term is defined in a note, which says that an MLIP is described in pim.
   - `description` is unchanged.

3. **`ml-model`** holds what the model is, how it was built and how good it is:
   - `algorithm*` and `target-variable*` are unchanged.
   - `input-feature` and `model-architecture` are unchanged.
   - A new optional, repeatable `architecture-parameter` is a generic parameter (0016) for numbers that fix the architecture, e.g. the number of layers or a cutoff radius. `model-architecture` explains their role, as ps `settings › description` does for `computation-parameter` (0067).
   - `model-size` is an int: the number of trainable parameters.
   - `training-data`, `training-method` and `model-performance` move inside `ml-model`, after `model-size`.

   An inference computation whose model is trained in another computation of the record gives only the required members, to identify the model.

4. **`training-data`** keeps its members. Two changes:
   - `dataset-split` stays a description in words, e.g. "random 80/10/10".
   - `source` is for data outside the record. Training data in the record is named as an input with the role Training data (0046).

5. **`training-method`**:
   - `training-procedure*` describes the overall fitting process: optimizer, learning-rate schedule, stopping rule, any active-learning loop and its selection criterion (0065 item 5). It also explains the role of each `hyperparameter` entry.
   - A new optional `loss-function` (string) gives the quantities fitted and how they are weighted.
   - `training-hyperparameters` becomes an optional, repeatable `hyperparameter`, a generic parameter (0016), for training settings only, e.g. learning rate, batch size, epochs. This settles 0001 A6 for ML.
   - `transfer-learning` is unchanged.

6. **`model-performance`**:
   - `validation` is replaced by `evaluation-method*`: how the model was assessed, e.g. a hold-out test set or k-fold cross-validation.
   - A new optional, repeatable `metric` holds one score. Its members:
     - `subset*`: open terms Training, Validation, Test;
     - `quantity*`: the target the score is for;
     - `measure*`: open terms, e.g. MAE, RMSE, R²;
     - `value*`: float, kind any;
     - `unit*`: a generic parameter's unit (0019).
   - `uncertainty-quantification` notes whether per-item uncertainties are part of the dataset.
   - A new optional `applicability-domain` (string) says where the inputs the model is applied to lie relative to its training data.

7. **A new optional `inference`** after `ml-model` describes how the dataset was produced from the model. Its members:
   - `input-data`: what the model was applied to. Data in the record is an input link instead.
   - `conditioning`: targets imposed on a generative model, e.g. space group, composition, property range.
   - `sampling-procedure`: how the outputs were drawn. It explains the role of each `inference-parameter` entry.
   - `inference-parameter`: repeatable, a generic parameter, e.g. sampling temperature or number of samples.
   - `number-generated`: int.
   - `filtering`: what was removed or kept, e.g. validity checks, deduplication, novelty against the training data, a stability pre-screen. Checks on a generated set (the share of valid, unique or novel structures) are given here, as they describe the output, not the model.

8. **`interpretability-method`** stays a member of `settings`, after `inference`.

## Consequences
- Applied in two kinds of pull request:
  - A structure pull request: `settings` and `computation-label`, the moves of items 3 and 8, the renames, and the introduction. It fills no typed field, as in mbpt (PR #111). examples/ml.json moves into settings, with `type` corrected to Structure generation, since WyFormer generates structures de novo.
  - The property pull requests of status step 5, in file order. Each adds the new members inside its property and fills the typed fields.
- No released instance breaks: ml's properties were legacy text in 0.6.0.
- PROPOSED, NOT DECIDED:
  - how pim records the fit of an MLIP, since it has no training properties;
  - a minimal `software` role for a trained model used by an inference computation;
  - whether `interpretability-method` belongs inside `ml-model`.
