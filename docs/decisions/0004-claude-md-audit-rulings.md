# 0004 — Rulings on the CLAUDE.md audit

Date: 2026-10-31. Status: accepted. Decided by: Ellad Tadmor.

## Context
CLAUDE.md stated a number of rules that no decision record backed. Each was reviewed one by one and ruled a decision, a proposal, or a correction. Rulings recorded elsewhere are not repeated here: the A3.3 removal (0001), the generic-parameter groups and the Annex U Rule 4 amendment (0001), and phase-field scaling (0003).

## Decisions
1. **Status of 0001.** Part A is accepted. In Part B, B1, B3, B4 (the unit), B6, B7, B8, B10 and B11 are accepted; B2 (the added note), B4 (the Ė symbol), B5 and B9 are proposals awaiting a decision; B12 needs no action. A6 is a proposal.
2. **GitHub organization.** The repository stays at `matcore-standard/matcore`. The name `matcore` is held by a dormant personal account; a GitHub support request to contact the owner is pending and unlikely to succeed. If `matcore` is released, whether to move to it or point it at `matcore-standard` will be decided then.
3. **Repository URL.** Only mkdocs.yml contains the repository URL. Other files link relative to the site or read it from mkdocs.yml.
4. **Baseline .docx.** The frozen Google Doc export stays in docs/decisions/ and is excluded from the published site. It remains downloadable from the public repository itself.
5. **Schema YAML is regular.** No YAML anchors or aliases, custom tags, includes or templating in schema files.
6. **Field set and order.** Each property entry has exactly the fields `name, required, description, type, extent, kind, recommended-unit, values, repeatable, [convention], [notes], [legacy_values], [legacy_unit], [subproperties]`, in that order. validate_schema.py will enforce the order.
7. **`any` is not limited to generic parameters.** `type`, `extent` and `kind` may be `any` wherever the schema leaves the field open and something else fixes it: the instance (generic parameters) or a required enumerated subproperty (e.g. `criterion` for the SCF tolerance, `basis` for exciton-momentum).
8. **Extent notation.** In YAML the open-length colon is quoted (`[":"]`); in prose and generated docs it is written `[:]`.
9. **Inapplicable kinds.** string, bool and file properties have kind `inapplicable`; a physical quantity is never typed as a string.
10. **Recommended unit.** Informative only; it must be an Annex U symbol whose kind matches the property's kind.
11. **Structured `values`.** `values` is structured and replaces the prose "Values" (0002). Its key set is a proposal.
12. **`legacy_*` fields.** The baseline prose is kept in `legacy_*` fields during migration and deleted once its content is transferred to the typed fields. The original wording remains in the baseline .docx and in git history (tag `v0.9-baseline`). A section is complete when no `legacy_*` fields remain.
13. **Names.** Names match `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`. A name is plural only when its value is a list (open extent); a repeatable property with a single value per occurrence stays singular. `unit` is singular.
14. **Terminology.** "Annex" for Annex U, which is normative. "Kind", not "Quantity kind", in the schema, the standard's prose and new text. Decision records are not rewritten. "Quantity kind" remains where it refers to QUDT's concept.
15. **Funding.** The MatCore effort is funded by NSF DMR Award #2404283 and supported through the KIM Initiative.
16. **Generic-parameter values** (added 2026-10-31). The instance type of a generic parameter's `value` is one of float, int, string, bool, matching the baseline wording of all five generic parameters. The type is stated in the instance, not inferred from how the value is written; each serialization defines how it is written. The value need not be a scalar: its extent remains `any` (0002).
17. **Serialization** (added 2026-10-31). §1.3 defines the term: "A *serialization* is a file format (for example XML or JSON) together with the rules that map the MatCore data model onto it." Elsewhere the term is used without naming formats.
18. **Instance serialization** (added 2026-10-31). The standard is agnostic to serialization format (§1.3). The XML examples in the standard are illustrative only and prescribe no format. Any serialization that preserves the property hierarchy, the required/repeatable semantics and the value/unit/convention structure is conformant. Which serialization(s) the MatCore tools read and write is a tool decision, not yet made, that does not bind other implementations; when it is made, a format-specific schema is generated from the YAML for that serialization and used by CI to validate the examples. The standard will state, in its own section, the requirements any serialization must satisfy. Normative text describes `unit`, `convention` and `basis` as subproperties; each serialization decides whether they become attributes, child elements or object keys. XML-specific wording in 0001 (A1.3, A10) and Annex U is to be checked when Part A is applied.
19. **Site address** (added 2026-10-31). The site is static, with no dynamic server (0000), and is served at matcore-standard.github.io/matcore for now. matcore.org will point to the GitHub Pages site as soon as it is clean and operational, replacing the current site there.
20. **Tools package** (added 2026-10-31). Decided: one Python package, run in-browser via Pyodide (0000). Proposed, not decided: the name `matcore`; its contents (a command-line validator; parsers for VASP, QE and LAMMPS output; web validator, visualizer and forms); parsers as the primary generator of instances with web forms as the fallback. Its serialization(s) are undecided (item 18).
21. **Website cleanup** (added 2026-10-31). The GitHub Pages site offers the user the same options as matcore.org so that it can replace it; the presentation may differ and should use the semantic structure of the YAML. Menu with navigation tabs: Home, About (About MatCore, Leadership), Standard (the standard, Revision History), Contact; `toc_depth` 2. The content of About MatCore, Leadership, Revision History and Contact is migrated from matcore.org as part of this task. Under Standard, each section shows its introduction and its example, as on matcore.org. `legacy_*` fields are hidden unless `--show-legacy` is passed, and CI builds with `--show-legacy` until every section is complete. Decision records are internal committee information and are not published on the site; the baseline .docx is excluded too (item 4). Open: the property layout, chosen after options are seen rendered; where section introductions and examples are stored; whether decision records must also leave the public repository.
22. **Decision records on GitHub, not on the site** (added 2026-10-31). Decision records, with the baseline .docx stored among them, stay in the public GitHub repository and are excluded from the site build. Site pages do not link to them. This settles the open point in item 21 and carries out the .docx exclusion of item 4.
23. **Section introductions and examples** (added 2026-10-31). Each section file `schema/<section>.yaml` has a top-level `introduction` (Markdown in a YAML literal block; one per section) and a top-level `examples` list. Each example entry has `caption`, `file` (an example instance in `examples/`), `source` (the dataset it documents) and optional `notes`. The text and examples are taken from the baseline .docx as they are. This settles the storage point left open in item 21.
24. **Typed-field migration, one property at a time** (added 2026-10-31). The unit of review is a top-level property with all of its subproperties: one pull request each, 48 in all. Each pull request first cross-checks the property against the baseline .docx (name, definition, values, required, repeatable, subproperty tree) and corrects any migration error, then maps its `legacy_*` fields to the typed fields, applying 0001 Part A to that property, and lists every judgment call in its description for a decision. 0001 Part A is applied this way rather than as a separate pass. The 0001 Part B fixes and the known baseline defects are applied before this work starts.
25. **Known baseline defects** (added 2026-10-31). The orbital basis set is named `localized-orbital-basis-set` in DFT and MBPT alike, replacing `localized-orbitals-basis-set` (DFT-4) and `local-orbital-basis-set` (MBPT-1), including references to it in notes. The mbpt.yaml note that refers to `basis-cutoff-planewave` is corrected to the property's name, `planewave-basis-cutoff`. The malformed baseline table MD-3 is checked against the .docx at md.yaml › particle-interactions / source. These are applied with the 0001 Part B fixes.
26. **Commit approval and scope** (added 2026-10-31). The separate Permissions rule is merged into the rule from 0005, so one rule covers approval and scope. Nothing is committed without the human's approval. A commit contains only what its message describes. An edit that the change itself makes necessary, such as a cross-reference it invalidates, belongs in the same commit and is named in the message; any other change outside the task is raised with the human first.
27. **Pull requests** (added 2026-10-31). One decision per change. Changes to `schema/`, the generated docs, or the site's build and content go through a pull request, so CI checks them before they reach `main`; the property pull requests (item 24) carry their judgment-call list in the description. Rulings and repository housekeeping may be committed directly to `main` once the human approves, one ruling per commit. The commit message references the decision record.
28. **Memory in the repository** (added 2026-10-31). Project memory lives in the repository, not in chat or in Claude Code's private memory, which the committee cannot see and which is not versioned. A decision made or changed is written into CLAUDE.md and its status list in the same commit as the work. The status list is updated whenever a step's state changes, so it is current even if a session ends without warning; at the end of a session it is checked and any correction committed.
29. **Pre-commit checks** (added 2026-10-31). Before every commit, the checks CI runs are run locally: `validate_schema.py`, `build_docs.py` and `mkdocs build --strict`. Files that `build_docs.py` regenerates are committed with the change, since CI fails if the committed copies are stale. Generated files under `docs/standard/` are never edited by hand.
30. **Units sourcing** (added 2026-10-31). QUDT identifiers, physical constants and unit symbols are never invented. `units.yaml` was verified against QUDT Units 3.3.0, GNU Units 2.23 (definitions.units 3.19) and NIST CODATA 2022. A new unit is added by pull request, with each of its fields (kind, QUDT identifier or null, GNU Units name, SI factor, source) traced to a primary source named in the pull request. A new kind needs a decision record.
31. **Order of serialization and tools work** (added 2026-10-31). The examples and the generated schema of status step 7 come after step 5, since a schema cannot be generated from unfilled typed fields; step 7 may run alongside step 6, and its format-agnostic requirements section may be written earlier. Step 7 opens with a decision record choosing the first serialization. The tools package (step 9) follows step 7 and uses that serialization; its validator reuses step 7's generated schema. With this item the audit of CLAUDE.md is complete.
32. **About and Leadership pages** (added 2026-11-01). Migrated from matcore.org with these changes: About's funding line uses item 15's wording; "(classical)" is dropped after Molecular dynamics; on Leadership, "Lead Organizers" becomes "Project Lead", listing Ellad Tadmor only, and "CMS" is spelled out as "computational materials science".
33. **PF example restored from matcore.org** (added 2026-11-01). The PF example in the baseline .docx lacks its first 26 of 68 lines (it starts at `<spatial-discretization>`; lost in the Google Doc export). Its remaining 42 lines are identical to the end of the PF example on matcore.org (standard version 0.3.0). The missing lines are restored from matcore.org. The Minimal example (in the .docx and on matcore.org) closes `<method-class>` with `</method>`; the closing tag is corrected to `</method-class>` so the example is well-formed XML. Both corrections are recorded here only; the published examples carry no note about them. The other examples are taken from the .docx as they are (0004 item 23).
34. **XML wording check closed** (added 2026-11-01). The check of item 18 finds no XML-specific wording in Annex U. 0001 A1.3 would add to §1.3 a sentence saying that the XML examples write `unit`, `convention` and `basis` as attributes, and that child elements are equally conformant. A1.3 is not applied: §1.3 already states that the XML examples are for clarification only and that the standard mandates no file format. A10 stays: it concerns the illustrative XML examples, which may write these subproperties as attributes. Nothing else changes.
35. **Order of the property pull requests** (added 2026-11-01). The pull requests of item 24 take the sections in the order minimal, dft, md, mbpt, ml, pf, derived, and the top-level properties within a section in file order.
36. **Marking a section complete** (added 2026-11-01). A section file whose typed fields are all filled declares `legacy_complete: true` at its top level. validate_schema.py fails if a file declares it while any `legacy_*` field remains. The field and the check are added to meta-schema.yaml and validate_schema.py as their own change.
37. **Typed fields of a container** (added 2026-11-01). A container, a property with subproperties and no value of its own, has `type`, `extent`, `kind`, `recommended-unit` and `values` all null. Its legacy text "Contains SubProperties as listed below" (and variants) is deleted with nothing to transfer, since the nesting states it.
38. **Title of the Minimal example** (added 2026-11-02). `title` is defined as "A single sentence description of the dataset", but the Minimal example's title is `Si_PRX_GAP`, a short label. The definition stays. The example's title becomes "Si_PRX_GAP: A foundational Density Functional Theory dataset with silicon configurations for training machine learning interatomic potentials", so that it follows the definition. As with item 33, the change is recorded here only; the published example carries no note about it.
39. **Recommended unit of a dimensionless property** (added 2026-11-03). When `kind` is `dimensionless`, `recommended-unit` is null: a dimensionless number carries no unit, so there is none to recommend. The case of kind `any` is not covered by this ruling. Amended by item 46; restored by item 48.
40. **Constituent concentrations sum to 100** (added 2026-11-03). The note of minimal `material-component` › `constituent` › `concentration` states that the concentrations of a material component's constituents sum to 100. The schema cannot express the rule, so it is reviewed by hand in the examples (0012); the instance validator of status step 9 may check it. Amended by item 46 (sum to 1).
41. **Species are chemical elements only** (added 2026-11-03). minimal `material-component` › `constituent` › `species` stays an enum of the 118 IUPAC element symbols. Isotope symbols (D, T) and pseudo-species (vacancies, coarse-grained beads, ghost atoms) are not added; a material component's `description` can state them until a need for more is shown.
42. **Long value lists render inline** (added 2026-11-03). build_docs.py keeps rendering an `enum` or `terms` list in full as one paragraph, however long (e.g. the 118 element symbols of `species`); no collapsed rendering is added.
43. **Pure numbers in §1.3** (added 2026-11-03). In §1.3's units paragraph (0001 A1.1), the sentence "Quantities of dimension one use the reserved symbol `dimensionless`" becomes "Where a `unit` is given for a pure number (a ratio or a count), as in a generic parameter or a nondimensional length, it is the reserved symbol `dimensionless`; a property whose Kind is `dimensionless` carries no `unit`." The SI term "dimension one" is not used, and the sentence agrees with 0015 item 3. Amended by item 46; restored by item 48.
44. **Type and Extent in §1.3** (added 2026-11-03). §1.3's list of a property's features gains, before Values, "Type: The data type of the Property's value: string, float, int, bool, file, or any (the instance states the type). A Property that only contains SubProperties has no type." and "Extent: The shape of the value, in KIM notation: [] for a scalar, [3,3] for a 3×3 array, [:] for a list of any length, or any when the schema does not fix it." The Values feature becomes "Values: The values the Property can take on, such as a controlled vocabulary, bounds, a format or a pattern, with examples."
45. **SubProperties in §1.3** (added 2026-11-03). §1.3's bullet stating that a Property with SubProperties is marked by the phrase "Contains SubProperties as defined in the table below" becomes "A Property that contains SubProperties shows them nested within it." The phrase was removed from the schema (item 37).
46. **Dimensionless values carry a unit; concentration is a fraction** (added 2026-11-04). Amends items 39, 40 and 43, following the second amendment of 0015. When `kind` is `dimensionless`, `recommended-unit` is `dimensionless`, the only Annex U symbol of that Kind. Minimal `material-component` › `constituent` › `concentration` is an atomic fraction from 0 to 1, not a percentage, and its note states that the concentrations of a material component's constituents sum to 1. No other property of the standard is expressed in percent. The last clause of item 43, "a property whose Kind is `dimensionless` carries no `unit`", no longer holds: §1.3 states instead that a dimensionless value's `unit` is `dimensionless`.
47. **k-point-spacing removed; mesh shifts are fractions; smearing takes generic parameters** (added 2026-11-04). dft `k-point-mesh` keeps `number-of-points` and loses `k-point-spacing`: the two describe the same mesh and can contradict each other, and the explicit number of points is the one a calculation can be reproduced from. 0001 A3.1's row for `k-point-spacing` (its `convention` subproperty) and B7 lapse with it. 0001 B5 is settled in A3.1's form: `shift` is three dimensionless fractions of the mesh spacing along the reciprocal lattice vectors, not an offset in 1/Å. `methfessel-paxton-order` is replaced by `smearing-parameter`, a repeatable generic parameter in the form of 0016, so that the parameters of any smearing method (the Methfessel-Paxton order among them) are recorded the same way; it is the sixth generic parameter of the standard.
48. **Dimensionless values are leaves again** (added 2026-11-04). Follows the third amendment of 0015 and reverses the unit parts of item 46: the recommended unit of a dimensionless value is null, as item 39 first ruled, and the last clause of item 43 ("a property whose Kind is `dimensionless` carries no `unit`") holds again. Item 46's ruling that `concentration` is an atomic fraction from 0 to 1, summing to 1, stands.
49. **Session practice** (added 2026-11-05). The working practices of the property pull requests are written into CLAUDE.md's working rules, so that a new session can resume without the conversation: keep CLAUDE.md, docs/decisions and anything else a new session needs current with the session's state at every step (rulings, open questions, and the state of the work in progress), checking before each turn ends that nothing said, found or decided exists only in the conversation; say so before switching branches, since the human's `mkdocs serve` shows the checked-out branch; commit a ruling on main and cut the pull request's branch from it; give each property pull request the description outline listed there and offer Auto-fix; after a merge, record it in its own status commit and delete the merged branch; mark a reversed or replaced status entry "(Superseded: …)" rather than rewriting it.
50. **FAIR data and AI readiness in §1.1** (added 2026-11-07). The first paragraph of §1.1 Objectives gains, at its end, the sentence "Its goals are to make computational materials data FAIR (findable, accessible, interoperable and reusable) and to contribute to its AI readiness." FAIR carries no link or citation; AI readiness is not defined, since the second paragraph's goal (3) says what it serves. The paragraph's double space in "guidelines for  documentation", a migration artifact, becomes a single space.

## Consequences
CLAUDE.md is updated to match, and every unbacked statement in it is marked PROPOSED, NOT DECIDED. Follow-up changes: exclude the .docx from the site build (4); tighten the name pattern in the meta-schema (13); add a field-order check to validate_schema.py (6); reword Annex U to "Kind" (14), as its own change now that Part A is applied property by property (24).
